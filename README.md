# Тестовое задание: оборудование в Битрикс24

Решение пяти задач из [todo.md](todo.md) для **коробочного Битрикс24**. Для каждого пункта выделен PHP-файл с пояснением. Структура `local/` готова для копирования в корень портала; файлы ядра не изменяются.

Код рассчитан на PHP 8.1+ и коробку с установленными модулями `crm`, `highloadblock`, `ui`, поддержкой смарт-процессов и нового API CRM (`Service\Container`, `Factory`, `Operation`). На старой коробке сначала нужно проверить наличие этих API. Дизайнер БП и роботы зависят также от редакции и настроек портала.

## Подключение и установка

1. Скопировать содержимое `local/` в `/local/` тестовой коробки, сохранив структуру каталогов. Включить также скрытые файлы компонента и каталог `.default`.
2. В **существующий** `/local/php_interface/init.php` добавить строку внутри PHP-кода:

   ```php
   require_once $_SERVER['DOCUMENT_ROOT'] . '/local/php_interface/figura/init.php';
   ```

   Если файла ещё нет, создать его с `<?php` и этой строкой. Регистрация обработчиков выполняется на каждом запросе; установщик при этом не запускается.

3. Авторизоваться администратором и открыть `/local/tools/figura/install.php`.
4. Нажать **«1. Создать структуру»**, затем **«2. Создать тестовые данные»**. Это два отдельных POST-запроса: между ними обновляются метаданные динамических сущностей. Установщик проверяет администратора и сессионный токен.
5. После второго шага перейти по выведенным ссылкам на сделку и элемент смарт-процесса. ID выдаёт портал, вручную прописывать их в коде не требуется.
6. Для проверки обычными сотрудниками настроить в CRM права на чтение созданного смарт-процесса и тестовой сделки. Установщик не выдаёт всем сотрудникам доступ автоматически. Пользователю №5 тоже нужны эти права.

Последовательный повторный запуск использует существующий HL-блок, тип, сделку, элемент и три записи оборудования. ID демосделки и элемента сохраняются в опциях модуля `main` с префиксом `figura_equipment_`; это служебные настройки решения, отдельный модуль устанавливать не нужно. Установщик рассчитан на запуск одним администратором. При ошибке предыдущие успешные действия сохраняются, исправление причины и повторный запуск продолжают установку. Если на портале обязательны дополнительные поля сделки, их нужно добавить в данные `createItem()` задачи 2; проверки CRM намеренно сохраняются.

## Как устроены данные

HL-блок имеет техническое имя `FiguraEquipment`, таблицу `b_figura_equipment` и русское название «Оборудование». Поля одиночные:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `UF_NAME` | `string` | Название оборудования |
| `UF_TYPE` | `enumeration` | Роутер, Ноутбук, Монитор |
| `UF_CREATED_TIME` | `datetime` | Дата и время создания |
| `UF_DEAL_ID` | `integer` | ID сделки |

В `UF_TYPE` записывается ID варианта списка, а не его название. Устойчивые `XML_ID` вариантов (`router`, `laptop`, `monitor`) используются при заполнении демоданных.

Смарт-процесс «Учёт оборудования» имеет код `FIGURA_EQUIPMENT`. Связь **Сделка → элемент смарт-процесса** создаётся через `RelationManager` на уровне типов и элементов. Поле `UF_DEAL_ID` относится к оборудованию, а связь смарт-процесса со сделкой — отдельная штатная связь CRM.

Смарт-процесс представляет собственную сущность CRM с карточками и стадиями. Бизнес-процесс — исполняемый сценарий действий над документом/элементом. В типе включены дизайнер БП и роботы; отдельный сценарий автоматизации бриф не задаёт. Сохранение элементов через `Factory → Operation → launch()` сохраняет штатные проверки и действия CRM.

## Компонент и вкладка

Компонент получает оборудование только одной сделки, поддерживает поиск по названию, фильтр по названию, типу и дате создания, сортировку и страницы по 10/20/50/100 записей. У фильтра и грида общий ID, включающий ID сделки. Пользовательские условия добавляются к обязательному `=UF_DEAL_ID`, поэтому сброс фильтра не открывает оборудование остальных сделок. Значения строк экранируются перед выводом.

Самостоятельный вызов компонента на странице коробки после подключения пролога:

```php
$APPLICATION->IncludeComponent('figura:equipment.list', '', [
    'DEAL_ID' => 123, // ID существующей сделки на вашем портале
    'CACHE_TYPE' => 'N',
]);
```

Обработчик `onEntityDetailsTabsInitialized` добавляет вкладку только в созданный тип смарт-процесса. Вкладка нового, ещё не сохранённого элемента отключена. Содержимое загружается через `loader.serviceUrl` при открытии вкладки. Сервер получает ID элемента, проверяет его доступность, находит родительскую сделку через `RelationManager` и проверяет права на неё. ID сделки из запроса не принимается. Нет связи — выводится предложение привязать сделку; неоднозначная связь с несколькими сделками тоже отклоняется.

Чтение оборудования разрешено сотруднику, имеющему право читать связанную сделку. Для вкладки дополнительно нужно право читать элемент смарт-процесса. Это явная модель доступа компонента: прямое обращение к ORM HL-блока само права CRM не проверяет. Редактирование оборудования остаётся в административном интерфейсе HL-блока.

## Счётчик в сделке

Обработчик `OnProlog` работает на стандартном маршруте `/crm/deal/details/{ID}/`, в том числе в слайдере. Он считает **все** записи HL-блока сделки через `getCount()` и подключает JS/CSS через `Asset`. Значение не зависит от текущего фильтра таблицы. Сделка без оборудования получает `0`.

JS размещает информационный блок сразу после CRM-поля с кодом `CLIENT`/`CLIENT_ID`. У блока нет редактора и элементов управления, он не добавляется в модель сохраняемых полей сделки. Для текущего пользователя с ID `5` сервер включает выделение фоном, полосой и жирным числом. Для остальных сотрудников оформление обычное.

Выбран вычисляемый блок, чтобы не хранить дубликат количества в пользовательском поле и не синхронизировать его при каждом изменении HL-блока. `MutationObserver` восстанавливает расположение после перерисовки редактора. Число пересчитывается при следующем открытии/перезагрузке карточки; обновления из других вкладок в реальном времени не реализованы.

Это место зависит от DOM веб-карточки CRM: после обновления её разметки нужно проверить селекторы в `deal-count.js`. Если «Клиент» скрыт в настройках карточки, его нужно вернуть для отображения счётчика под ним. Для нестандартного маршрута сделки адаптируется проверка пути в задаче 5. Мобильная карточка этим решением не расширяется.

## Проверка

В среде подготовки нет ядра и БД Битрикса. Локально доступны проверка синтаксиса и автономные проверки построения фильтра/сортировки; они не подтверждают выполнение ORM, событий и UI на реальном портале.

```powershell
$phpFiles = rg --files --hidden -g '*.php' -g '!.git'
foreach ($file in $phpFiles) { php -l $file; if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE } }
php tests/query_test.php
node --check local/js/figura/equipment/deal-count.js
```

Проверки после установки на коробку:

1. В HL-блоке есть четыре поля, три варианта типа и три записи тестовой сделки. Повторить оба шага установки: дубликаты не появляются.
2. В элементе смарт-процесса есть привязка к тестовой сделке и вкладка «Оборудование» с тремя строками.
3. Фильтр по типу «Ноутбук» оставляет одну строку. Проверить поиск, диапазон даты, сортировку и сброс фильтра. Для пагинации добавить более 20 записей через админку и проверить вторую страницу и изменение размера.
4. Привязать элемент к другой сделке и заново открыть вкладку: показывается оборудование новой сделки. Без связи отображается пояснение, оборудование других сделок не раскрывается.
5. В тестовой сделке под «Клиентом» стоит число `3`; фильтр таблицы на него не влияет. Добавить/удалить запись в HL-блоке и перезагрузить карточку: количество меняется. В другой сделке без оборудования стоит `0`.
6. Проверить просмотр и редактирование сделки: счётчик остаётся неинтерактивным. Под пользователем №5 он выделен, под другим — нет. Проверить полную страницу и слайдер.
7. Под сотрудником без доступа к сделке/смарт-процессу данные недоступны, включая прямой AJAX-запрос с изменённым ID. Запрос вкладки без сессионного токена возвращает `403`.

Ошибки пишутся через `AddMessage2Log` с источником `figura.equipment` / `figura.equipment.install` в журнал, настроенный на портале. Установщик показывает администратору причину ошибки; компонент не раскрывает технические детали пользователям.

Для отключения убрать строку подключения из `/local/php_interface/init.php`. Сущности и записи останутся в портале; автоматическое удаление данных не выполняется.
